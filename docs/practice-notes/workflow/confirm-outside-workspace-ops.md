## 场景

需要改动工作区之外的文件或全局配置时：`~/.ssh/config`、git 全局配置、凭据管理器、用户主目录下的脚本，以及删除、移动工作区外的目录。自动化代理（agent）代用户执行这类操作时尤其适用。

## 做法

1. 执行前先说明四件事：**改哪个文件、加入什么内容、影响哪些后续行为、风险与回滚方式**。
2. 一次只做一个操作，不要和无关改动打包进同一条命令。
3. 需要提权（如完整磁盘/网络权限）时，明确说明为什么普通权限不够。
4. 等用户明确同意后再执行；「改回去」「修一下」这类指令只覆盖它字面指向的对象，不隐含授权其他文件。
5. 被拒绝就停下解释，不换一条路径重试。

## 原因

`~/.ssh/config`、凭据和 git 全局配置会影响这台机器上**所有**仓库和所有 SSH 连接，一次误写可能把认证导向错误主机，或让后续排障失去可信基线。把多个操作打包，会让用户无法单独否决其中危险的一项；提权弹窗只是权限门禁，不等于用户已经知情同意。

## 反例

为把 remote 从 HTTPS 改成 SSH，在一条 `danger-full-access` 命令里同时写入 `~/.ssh/config`（Host 别名 + 端口 443）并执行 `git remote set-url`。用户只说过「给我改回去」，并未同意改 SSH 配置，命令被拒绝。正确做法是先给出配置内容与风险，单独征求同意。
